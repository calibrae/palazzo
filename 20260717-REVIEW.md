# palazzo — code review

- **Date:** 2026-07-17
- **Tree:** `main` @ `8490b97` (v0.14.2 code `0b846db` + nxp GitLab merge)
- **Scope:** whole codebase (~6,300 LoC Rust) + CI/Docker/systemd/deps
- **Method:** 6 parallel review subagents over module groups, plus orchestrator
  independent verification of every Critical/High from source. `cargo
  test`/`clippy`/`fmt`/`audit` run. Every finding below with a `file:line` was
  read directly, not taken on an agent's word.

---

## Bottom line

Mechanically the code is well-built — 68 tests green, clippy/fmt clean, the
hand-rolled JWT is sound (constant-time MAC, no alg-confusion), Qdrant filters
are injection-proof, the embedder threading is careful. The problem is
**architectural: palazzo was built single-tenant/trusted and now runs
multi-tenant (hundreds of devs), but the auth layer only does *write
attribution* — it never does *read/delete authorization*.** That gap, plus one
unauthenticated bulk-read endpoint, is the headline.

Separately, a dependency CVE published after v0.14.2 shipped is **currently
failing `cargo audit` in both CI pipelines and blocking the NXP ArgoCD deploy.**

**The through-line for #1–#4:** authorization was never built, only attribution.
If the hundreds of devs are mutually-untrusted, that architecture is the thing to
fix (thread verified identity into every read/delete/supersede and force it into
the filter server-side; the `authenticate()` seam in `oauth.rs` is where a real
IdP goes). If they're mutually-trusted and the network perimeter is the real
gate, then `/export` (#1) and the CVE (#8) are still must-fix regardless.

## 🔴 Critical

### C1 — `GET /export` has no authentication, in any mode
- **Where:** `main.rs:779-781` (route), merged with no guard at `main.rs:862`;
  the comment at `main.rs:800-803` lists it as "stays open".
- **Impact:** `/mcp` and `/ingest` get `require_auth`; `/export` next to them is
  wide open even with `PALAZZO_AUTH=email`. `curl $HOST/export?vectors=true`
  streams the **entire** collection — every tenant's text, wings, `author`
  emails, and 768-dim vectors — as NDJSON, no token. Writes are gated but the
  bulk read isn't; that asymmetry reads as an oversight, not a design choice. If
  nginx is expected to gate it, that's undocumented and doesn't cover the
  systemd/homelab boxes.
- **Fix:** layer `require_auth` onto `export_route` when auth is enabled.

### C2 — No caller identity reaches the read / delete / supersede tools
- **Where:** `palace_find` (`mcp.rs:349`), `palace_recall` (`mcp.rs:361`),
  `palace_delete` (`mcp.rs:404`), `palace_delete_by_filter` (`mcp.rs:416`) take
  **no `extensions` parameter** — contrast `palace_store` / `palace_store_batch`
  / `palace_supersede` (`mcp.rs:326,339,394`) which do and derive `author` from
  the verified token. Enforcement gap confirmed at `do_delete_by_filter`
  (`mcp.rs:1103-1155`): the only precondition is "one of
  wing/category/room/hall/author/since/until" (`:1116-1128`), and `author` is a
  bare client field (`:1147`).
- **Impact:** `author` is server-stamped on *writes* (unspoofable — good) but is
  just an optional client *filter* on reads/deletes. `{wing:"projects"}` alone
  mass-deletes every tenant's project memories (cap 1000/call);
  `{author:"victim@corp"}` erases a named colleague's whole bank; `palace_find`
  with no filter reads everyone's memories; `palace_recall` does no filtering at
  all and IDs are low-entropy/enumerable; `palace_taxonomy` enumerates every
  contributor's email. `confirm`/`expected_count`/`dry_run` are fat-finger rails,
  not authorization — any caller satisfies them. **More severe than C1 because
  it's destructive, and `palace_delete_by_filter` is explicitly marketed for
  cross-user GDPR erasure.**
- **Fix:** thread verified identity into `do_find`/`do_recall`/`do_delete`/
  `do_delete_by_filter`/`do_supersede` and force it into the filter (or an
  ownership check) server-side; never trust `args.author` as more than a hint.
  Require operator scope for any filter that omits `author`.

### C3 — Identity is self-asserted; no proof of ownership
- **Where:** `email_allowed` (`auth.rs:140-150`) checks only shape + optional
  domain; `whoami_post` (`auth.rs:272-298`) and `authorize_post`
  (`oauth.rs:218-237`) then mint a token. Empty allowlist (the default) accepts
  any email.
- **Impact:** `curl -X POST $HOST/whoami --data-urlencode email=ceo@nexpublica.fr`
  returns a live ~30-day token stamped as the CEO — no OTP, no SSO, no
  verification. Documented ("attribution, not authentication… not a defence
  against a malicious insider"), so it's known — but combined with C2 it means
  **even fully configured, the auth layer provides zero tenant isolation**, and
  in `off` mode `/mcp` isn't gated at all.
- **Fix:** magic-link/OTP before minting, or wire the `authenticate()` seam
  (`oauth.rs:9-11`) to a real upstream IdP before multi-tenant use.

### C4 — OAuth `redirect_uri` accepts any https host → account-takeover primitive
- **Where:** `redirect_uri_ok` (`oauth.rs:113`) is `"https" => !host.is_empty()`;
  DCR never binds `redirect_uri` to a `client_id` (`oauth.rs:151-167`,
  `:222` treats it as untrusted).
- **Impact:** attacker sends a victim an `/authorize` link with
  `redirect_uri=https://attacker.tld/cb` + the attacker's own PKCE challenge;
  victim logs in; the code 302s to the attacker, who redeems it at `/token` for
  the victim's tokens. PKCE doesn't help — the attacker *is* the flow initiator.
  `git show 0b846db -- src/oauth.rs` confirms the v0.14.2 pass hardened the
  *loopback* branch (killed `localhost.evil.com`) but left the https branch's
  "accept any host" untouched — **the hardening fixed the wrong branch.** This is
  the bypass around a domain allowlist. (A `\`-based loopback variant,
  `http://evil.com\@localhost/`, also slips the host-exact check and is
  misresolved by WHATWG clients — redundant with the https hole, same fix.)
- **Fix:** allowlist redirect hosts (config-driven), or bind `redirect_uri` to
  the `/register` value keyed by `client_id` and require exact match.

## 🟠 High

### H1 — `new_id()` collides across replicas → silent data loss
- **Where:** `mcp.rs:1462,1474-1488`. `NEXT_ID` is a process-local `AtomicU64`.
- **Impact:** monotonic and collision-free *within* a process (the concurrency
  tests are correct), but two replicas each start at 0 and both clamp to
  `floor = now_millis`, so same-millisecond stores on different replicas mint the
  **same ID** and the second `upsert` silently overwrites the first — permanent,
  undetected loss. Applies to multi-replica **and** the old-pod/new-pod overlap
  of every rolling ArgoCD deploy. The comment at `:1458` ("concurrent calls can
  never mint the same ID") is only true single-process.
- **Fix:** UUID point IDs, or fold a per-replica salt into the counter's low bits.

### H2 — WAL isn't durable and can tear
- **Where:** `wal.rs:79-82`. `append` opens `.append(true)` + `writeln!`, **no
  `sync_all`/`sync_data`** — yet `log_strict`'s contract (and CLAUDE.md) call it
  "durably appended… the only audit trail".
- **Impact:** power-loss between the WAL write (still in page cache) and the
  Qdrant delete → point gone, audit record gone. Also `writeln!` on the
  unbuffered `File` is two `write()` syscalls (content + `\n`), so two concurrent
  deletes can interleave into a torn/corrupt line — in exactly the audit trail
  the destructive-delete design depends on.
- **Fix:** `write_all(format!("{line}\n").as_bytes())` in one call +
  `sync_data()` before `log_strict` returns Ok.

### H3 — `/health` always returns HTTP 200
- **Where:** `main.rs:472-488` returns `axum::Json` (always 200) with a literal
  `"status":"ok"`; Qdrant-down only shows as a nested `"qdrant":"down"`.
- **Impact:** defeats both the Docker `HEALTHCHECK` (`Dockerfile.cloud:44`,
  `curl -fsS`) and any k8s HTTP probe — the pod is "healthy" forever while every
  operation fails, and k8s never restarts it.
- **Fix:** return `(StatusCode::SERVICE_UNAVAILABLE, …)` when `qdrant_up` is false.

### H4 — RUSTSEC-2026-0204 (crossbeam-epoch 0.9.18) is blocking the deploy pipeline
- **Where:** `Cargo.lock` (via `metrics-exporter-prometheus` and
  `fastembed`→`rayon`). Advisory dated 2026-07-06, after v0.14.2 shipped.
- **Impact:** both `ci.yml` and `.gitlab-ci.yml` run `cargo audit --deny
  warnings`, and the GitLab `security` stage gates `package`→`deploy`, so **the
  NXP ArgoCD deploy is currently blocked**, not just a red check.
- **Fix:** `cargo update -p crossbeam-epoch` → 0.9.20 (dry-run confirmed:
  semver-compatible patch bump, no other churn).

### H5 — `palace_check_duplicate` skips the size gate and diverges from real dedup
- **Where:** `mcp.rs:1313-1330`.
- **Impact:** embeds `args.text` with no `MAX_TEXT_BYTES` check, while
  `do_store`/`do_find`/`do_supersede` all check first — the one tool documented
  as a *cheap pre-flight* lets a 10 MB payload straight into the embedder. It
  also uses a different dedup rule than `do_store` (top-1 score-only vs top-5
  score **and** byte-exact text), so it gives wrong duplicate signals both ways
  (false positive skips a genuinely-distinct store; false negative at rank 2–5
  reports "not duplicate" when `do_store` would have deduped).
- **Fix:** add the `MAX_TEXT_BYTES` check; reuse `exact_dup`-over-`DUP_SEARCH_K`.

### H6 — Write path guards vector *count* but never *dimension/model*
- **Where:** `mcp.rs:610` checks `vectors.len() != valid_texts.len()`; nothing
  asserts `len()==768`; `qdrant.rs:157-192` forwards as-is; `schema.rs` has no
  model-provenance field.
- **Impact:** Qdrant rejects a wrong-*dimension* vector loudly at upsert — fine —
  but a *same-dimension, different-model* vector sails through and silently
  poisons the shared space with no error/log/metric. That's the "do NOT re-embed
  with another model" invariant CLAUDE.md calls the hardest one, unguarded beyond
  raw dim. Practical exposure is mostly the non-default Ollama backend
  (`OLLAMA_MODEL` drift, or the `nomic-embed-text` tag resolving to different
  weights over time) since prod fastembed pins the model in source; the Ollama
  batch path checks response *count* only (`ollama.rs:126-136`).
- **Fix:** assert `len()==768` immediately after every embed; stamp a `model`
  field into `Payload` so drift is auditable via `palace_taxonomy`.

### H7 — `/v1/embeddings` is unauthenticated and shares the one embedder mutex
- **Where:** `main.rs:789-798` (no auth, no rate-limit layer); the embedder is a
  single process-wide `Arc<Mutex<Inner>>` (`main.rs:706-720`,
  `fastembed_backend.rs:33`), and `embed_batch` holds the lock across all chunks
  (`fastembed_backend.rs:206-217`).
- **Impact:** an anonymous caller floods `/v1/embeddings` (bounded to 512×32 KB,
  but no route rate-limit and axum's default 2 MB body cap applies) and every
  request serializes on the same lock — starving every authenticated
  `palace_store`/`palace_find`/`/ingest` in the process. The auth boundary the
  operator turned on is bypassed via a sibling route sharing the mutex.
- **Fix:** gate `/v1/embeddings` behind `require_auth` (and/or the rate limiter)
  when auth is enabled; consider releasing the lock between chunks.

## 🟡 Medium

### M1 — SIGTERM not handled
`main.rs:879-886` only awaits `ctrl_c()` (SIGINT). k8s and systemd send
**SIGTERM** → OS default-kill, the `CancellationToken` drain never runs,
in-flight `/export`/`/ingest` streams cut mid-write. **Fix:** `tokio::select!`
on `ctrl_c()` and a `SignalKind::terminate()` listener.

### M2 — Delete WAL omits `author`
`mcp.rs:~1049` (`do_delete`), `~1249` (`do_delete_by_filter`). After a GDPR
erasure the WAL is the only surviving record and it captures what/why (as typed
by the caller) but never *who* issued the call — even though `Memory`/
`ExportPoint` carry `.author`. **Fix:** add `extensions`, thread `author_from`,
log it.

### M3 — `do_supersede` upserts the new point before retrieving the old ones
`mcp.rs:958-964`. A transient Qdrant error on the retrieve (`:964`, `?`) after
the upsert (`:958`) succeeds orphans the new point and returns total failure to
the caller; with no dedup on supersede, a naive retry creates a second successor
while the originals stay unmarked — two contradictory "current" facts. **Fix:**
retrieve/validate before upserting, or clean up the orphan on failure.

### M4 — Rate-limit key is attacker-spoofable
`ratelimit.rs:57-65` trusts the first `X-Forwarded-For` hop. A random header per
request lands every request in a fresh bucket → the 60/60s limit never engages on
`/whoami`, `/authorize`, `/token`, `/register`. Secondary: past 10k spoofed keys,
each `check()` does an O(map) `retain()` under the single global mutex. **Fix:**
key on `ConnectInfo` peer addr unless a trusted-proxy-hop count is configured.

### M5 — `PALAZZO_ALLOWED_HOSTS=""` fails open silently
`main.rs:683-704`. A set-but-empty env (templated CI/Helm footgun) yields an
empty allow-vec → rmcp allows all hosts (DNS-rebinding protection off), but only
logs an innocuous `info` — unlike the explicit `*` path, which logs a loud
warning. **Fix:** treat empty-string as unset (fall through to the localhost
default); only disable via the `*` sentinel.

### M6 — `ensure_collection` never validates an existing collection's dim/distance
`qdrant.rs:416-456` inspects only the GET status, never
`config.params.vectors`. A mis-set `COLLECTION` pointing at a wrong-model 768-dim
collection is silently accepted → permanently wrong search. **Fix:** on the
200 path, assert `size==768 && distance=="Cosine"`.

### M7 — Startup fails open on provisioning errors
`main.rs:304-306,625-627,670-672` warn and serve anyway when
`ensure_indexes`/`ensure_collection` fail — turning one boot failure (or a
lost `ensure_collection` race between booting replicas) into an ongoing wall of
per-request errors. **Fix:** treat provisioning failure as fatal / retry before
serving.

### M8 — No Qdrant API-key support
`qdrant.rs:138-147` — no `Authorization`/api-key header anywhere. Data-layer
security rests entirely on network reachability to `10.10.0.3:6333`; zero
app-layer defense if that boundary widens (k8s/S3NS). **Fix:** optional
`QDRANT_API_KEY` env → header.

### M9 — Qdrant/`reqwest` client rebuilt per MCP session
`main.rs:728-732` factory → `make_palace_with_embedder` → `Qdrant::new()`
(`qdrant.rs:138-143`, `.expect("reqwest client")`) runs on **every** new session.
The embedder is deliberately shared (one Arc), but a fresh `reqwest::Client` —
new connection pool, new TLS config — is built per session, defeating pooling,
and the `.expect()` is a latent panic on that hot path. **Fix:** build one
`Client` at startup and share it like the embedder.

### M10 — Unbounded MCP session accumulation
`main.rs:680-682` (`accept_unknown_sessions`) + `:725-726` (`keep_alive = None`)
→ any POST with an unknown session-id creates a session that never expires,
reaped only on restart. **Fix:** cap concurrent sessions or set a bounded idle
timeout.

### M11 — `/ingest`: all-or-nothing parse, no item cap, no rate-limit
`main.rs:440-449` — one malformed NDJSON line aborts the whole request (a status
already committed as 200 before streaming, `:460-461`), silently abandoning all
remaining items; a status-only client believes it succeeded. Only a byte cap
(64 MiB), no item-count cap and no rate limit (`:771-774`), and each item does a
sequential awaited dedup search under the shared embedder mutex. **Fix:**
per-item best-effort parse (match downstream semantics), an item cap, and a
rate-limit layer.

### M12 — `do_store` TOCTOU on concurrent identical stores
`mcp.rs:470-557`. The intra-batch `seen_text` fix only covers one
`palace_store_batch` call; two separate concurrent `palace_store` calls with
identical text each run their dedup search before either upserts → duplicate
points, reintroducing the class the v0.14.2 pass closed. **Fix:** deterministic
hash-derived ID for the dedup check, or a per-text lock.

### M13 — rmcp `allowed_origins` never configured
`main.rs` never calls `with_allowed_origins`, and there's no env knob; rmcp's
default `vec![]` disables Origin validation entirely. Combined with M5, both
anti-rebinding layers can end up off (one by omission, one by misconfig).
**Fix:** add `PALAZZO_ALLOWED_ORIGINS` mirroring the hosts knob.

## ✅ Verified solid (ruled out — don't re-litigate)

- **JWT (`auth.rs`):** constant-time `verify_slice` (subtle-backed), `exp`/`typ`
  enforced, 3-part structure enforced, algorithm hardcoded to HMAC-SHA256 →
  immune to `alg:none`/algorithm-confusion despite being hand-rolled. base64url
  encode/decode consistent (`URL_SAFE_NO_PAD`), fails closed.
- **Qdrant filters: no injection.** Values are inserted as `serde_json` string
  leaves via `json!` (structured tree, not string concat) — crafted field content
  can't escape the intended clause. The real issue is C2 (nothing forces the
  `author` clause to be present), not injection.
- **OAuth mechanics:** PKCE S256 unconditional (no `plain` downgrade),
  authorization codes single-use via atomic `remove` (no replay/TOCTOU), code TTL
  + capacity cap enforced, domain-allowlist matching is exact lowercase (no
  suffix/prefix bypass). PKCE compare isn't constant-time but the challenge is
  public — not exploitable.
- **Normalization is NOT a bug.** fastembed L2-normalizes and the Ollama path
  doesn't, but the collection is Cosine (`qdrant.rs:439`) and Qdrant
  re-normalizes internally at upload+query, so client-side magnitude is
  irrelevant to the score. Don't chase it.
- **Embedder:** ONNX inference correctly on `spawn_blocking` (never blocks the
  async runtime), output pinned 768-dim, RSS recycler is race-safe (rebuild
  off-lock, sub-ms pointer swap, single-flight, JoinError-handled),
  `Arc<Mutex<Inner>>` + `blocking_lock` is the right pattern. Model-load is
  `Result`-based (startup-only, clean exit on failure). `OLLAMA_URL` SSRF ruled
  out (operator env, never request-derived).
- **`new_id`** is provably monotonic/unique single-process (H1 is cross-process
  only); the `.expect` in its `fetch_update` closure is unreachable.
- **Write attribution is unspoofable** — `author` on `palace_store`/`_batch`/
  `supersede` is server-derived from the verified token; the arg structs have no
  client `author` field.
- **Config fails closed:** `PALAZZO_AUTH=email` with a missing/short signing key
  `bail!`s at startup. `PALAZZO_BIND` defaults `127.0.0.1`. No `panic=abort`, so
  a handler panic unwinds its task without killing the server. No CORS layer (so
  no `ACAO:*`-with-credentials footgun) — the gap is the opposite (M13).
- **systemd unit** is well-hardened (`NoNewPrivileges`, `ProtectSystem=strict`,
  scoped `ReadWritePaths`, etc.). Runs as non-root UID 1000.
- `cargo test` 68 passed · `cargo clippy --all-targets` clean · `cargo fmt
  --check` clean.

## Recommended fix order

1. **`cargo update -p crossbeam-epoch`** (H4) — one line, unblocks CI + the NXP
   deploy. Do this first.
2. **Clear-cut, low-risk bug fixes:** `/export` auth (C1), `/health` 503 (H3),
   SIGTERM (M1), WAL fsync + single-write (H2), `check_duplicate` size gate (H5),
   post-embed `len()==768` assert (H6). None involve a design decision.
3. **Decide the trust model.** If devs are mutually-untrusted: build read/delete
   authorization (C2), real identity verification (C3), and lock down the OAuth
   redirect allowlist (C4). If the perimeter is the gate: document that
   explicitly and ensure every box (incl. homelab systemd) actually enforces it.
   Hold on the isolation redesign until this is decided — it's a product call,
   not a mechanical fix.
4. Work the Medium/Low list as capacity allows; M4/M5/M13 (rebinding + rate-limit
   spoofing) matter most if the HTTP surface is ever reachable beyond a trusted
   perimeter.
